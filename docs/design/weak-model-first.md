# Weak-model-first allocation: delivery plan

## Goal and complete result

Make the default collaboration preference explicit: when quality, authority and independent verification are established, prefer the configured weaker Pi model for the largest reasonably self-contained outcome. Codex resolves essential design uncertainty, clarifies facts and independently reviews delivery. Choose allocation using time to accepted delivery and all attributable costs. Direct Codex completion and early takeover remain valid when supported by concrete evidence.

Deliver a coherent 0.8.3 policy/documentation release. This first real maintenance outcome is delegated as one block: inspect active guidance, revise the policy and task packet, reconcile release metadata and version assertions, run the required checks, and commit a reviewable candidate. The worker chooses wording and routine implementation. A documentation delivery can establish that this work was delegated successfully; it cannot prove general coding capability or a speed/cost advantage.

## Verified baseline and boundaries

The implementation baseline is 0.8.2 (`dc6aa2d`). It already provides explicit early takeover, task-frozen eligibility, exact quality counts, immutable evidence and Pi-only cost coverage. The active Skill currently gives a neutral choice between direct Codex completion and bounded design followed by Pi. No runtime mechanism is required to express the new preference.

The Skill remains the single policy authority. Task-packet and runtime references describe its use. Historical designs retain their original evidence and are marked historical when necessary to prevent obsolete guidance from competing with the current policy. Change canonical source only; generated installation sources and managed caches are handled after main acceptance through the formal installer.

Scope: active collaboration guidance, relevant documentation, release metadata and existing version assertions. Runtime algorithms, model lists/defaults, task/round state, failure limits, budgets, credentials, transport and hooks are protected. Keep the frozen design file unchanged during implementation. No new classifier, allocation score, token quota, task database, approval gate or mandatory model discussion is needed. Preserve others' changes; report an actual scope conflict rather than expanding silently.

## Allocation decisions

- Define the outcome before choosing its executor. A coherent result can cross files and layers and includes investigation, implementation, integration, verification and ordinary repairs. Bound it by dependencies, feedback and independently observable completion.
- Prefer Pi when the necessary facts are accessible, consequential interfaces/invariants are settled, genuine feedback is available and the remaining authorized resources can support delivery. A complete read-only investigation also qualifies.
- Codex resolves only consequential unknowns before dispatch; Pi retains freedom to read original sources, choose routine implementation and fix ordinary failures. Avoid both an entire-history prompt and mechanical step-by-step fragments.
- Direct completion or early takeover needs a concrete task-specific reason, such as unresolved cross-state semantics dominating the remaining work, unavailable trustworthy feedback, or evidenced repair/coordination cost exceeding the likely remaining benefit. A brief reason belongs in the existing task/design or review record; do not add a separate form or demand precise cost data that is unavailable.
- Review at complete delivery or a material evidenced anomaly. A red test, confidence score, changed-file count, model label or token share alone does not select a route. Continue the same Pi session when repair is worthwhile; preserve the existing hard limit and early-takeover guards.
- Improve turnaround with accurate facts, selective/batched reads, cheap discriminating checks and exact final acceptance. Parallelize only independent complete outcomes when existing capacity and shared-resource ownership allow it; this policy does not raise capacity.
- Maximize useful weak-model work, not token consumption. Record known Pi usage, elapsed time, failures and Codex design/review/takeover or external help in their actual scopes. Unknown cost remains unknown. Increase outcome size or reduce guidance only when later comparable results justify it.

Counterexamples for main review: a stable cross-file repair should be eligible as one Pi outcome; a missing restart/effect invariant needs Codex design before delegation; repeated ineffective repair can warrant early takeover; more tokens with slower acceptance is not success; unavailable billing cannot support a savings claim. These are review examples, not production routing rules or a new evaluator.

## Execution and acceptance

1. Main freezes this design, a short private brief and the phase contract at an exact baseline; one Pi writer receives the whole outcome in a separate worktree.
2. Pi reconciles active guidance and prepares 0.8.3 metadata/version assertions. Use existing cheap version checks while editing; preserve genuine behavioral tests and their original pass conditions.
3. Pi commits a clean candidate and runs the full Python suite and public privacy scan with the frozen check helper. Preserve failures and original logs. Do not add tests that merely assert prose wording.
4. Main reviews the exact diff, actual check receipts and semantic counterexamples. If accepted, integrate the exact candidate locally and install through the existing formal local marketplace. Verify installed version and tracked runtime/skill file identities. No public push is part of this outcome.
5. Use subsequent genuine maintenance needs to assess the larger-outcome preference. Select only the comparison arms needed for an adoption decision, keep task facts/acceptance comparable, isolate candidates and retain all failures/help. Product-Bot self-maintenance and its existing prerequisites remain separate from external plugin construction evidence.

The dispatch contract bounds this outcome to 2400 seconds, with individual commands capped at 900 seconds, one writer and serial checks. The last full Python suite contained 468 tests and took about 428 seconds; reserve time for that real check, review and ordinary repair. Missing required evidence remains incomplete. A transport incident preserves the session, candidate and spend; it is not a quality rejection. Main performs scoped local integration and formal installation after acceptance.
