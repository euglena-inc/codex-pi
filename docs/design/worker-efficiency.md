# 插件执行效率：收敛后的实施计划

## 目标、范围与当前状态

保留 Python 控制层和 Pi 原生 TypeScript 扩展。优先缩短实际执行墙钟时间，减少重复检查、预算不足的启动、日志内存复制和无效上下文往返；正确性、完整最终验收、失败原证和恢复行为不退化。

本轮只修改 codex-pi 插件、它的测试/验证程序及协作指引。消费项目的49个子检查、业务测试去重、产品fixture/Docker配置和其他聊天活动worker不在写入范围；其耗时仅作为需求依据。Rust重写、新服务、新数据库、通用DAG调度器、自动缓存PASS、推送/发布/重装均不在本轮。

当前：检查预算与局部修复已完成并通过同task/session的新runtime自用验收，见 [验证记录](../validation/check-budget-0.7.1-20261003.md)。325项完整回归、10项真实Pi探针通过；路线B也已通过主会话接管修复和完整验收，见 [流式与统计验证](../validation/runtime-efficiency-0.7.1-20261003.md)。路线C也已由用户授权主会话接管完成，见 [并发验证](../validation/check-concurrency-0.7.1-20261003.md)。剩余路线D的准确设计见 [context-workflow.md](context-workflow.md)，尚未实施。旧brief/helper/合同不改写，后续接口和可执行验收均基于前驱实际接受候选冻结。

## 架构决定

- Python继续拥有task/round预算、监督进程、检查回执、SQLite看板和恢复；TypeScript仅接入Pi工具事件、守卫、codemode与会话生命周期。保留每轮CLI JSONL和Codex queue。
- 单个项目 maxWorkers 维持1；利用多核首先并发独立本地工具/检查，不增加模型worker或并行修改同一工作树。
- 现有 resourceLimits/maxBytes 是目录磁盘字节限制，不能称为RAM保护。内存观测、并发准入和磁盘限制分别命名、分别验证。
- 性能改动进入现有函数/数据投影；共享逻辑确需抽取时才加小模块。不要为每个优化点各造一套状态、日志、runner或配置。

## A. 先完成已派发核心机制

预算准入复用真实轮次deadline、预计耗时、命令上限和收尾余量。targetedCommand引导局部修复，final:true/干净候选触发完整检查；局部绿不能替代正式验收。

主会话接受阶段A且所有writer释放后，沿同task/session采用新helper，阶段B真实使用：预计时间超过余量的check被拒且无子进程/回执；全量缺final被拒；局部检查实际成功；固定候选后完整Python回归、真实Pi/QuickJS和隐私检查通过。只用拒绝反例，不真的耗尽预算。本阶段独立完成后再开始下面的性能代码改动，避免当前任务范围膨胀。

## B. 先取得插件自身基线，再降低内存与观测开销

复用同一套私有合成验证材料记录：检查墙钟、模型响应区间、工具区间并集、排队/未结束/未知时间、token与缓存构成、插件进程RSS、读取字节数、检查次数。控制层和实际子命令分开；不能把工具等待算作Python计算，也不能把父子时长相加。

### 流式日志处理

优先修复已确认的整日志read_bytes→decode→多次扫描：用固定大小字节块计算SHA-256，增量解析计数，保留有限尾部。保持最后一个合法/非法unittest摘要的原有保守语义、Go计数优先级、UTF-8跨块处理和无计数unknown。超长单行不能形成无限缓冲，也不能截断后误认通过。原始日志仍完整落盘，回执格式兼容。

验证同样内容在小块/大块、多字节边界、超长单行、冲突摘要、空/截断日志中的hash/计数/尾部一致。用10MiB和200MiB合成日志的独立子进程比较旧/新实现RSS、耗时；大日志新增内存不应与文件大小线性增长。不得以小日志正确冒充大日志有界。

### 指标与刷新

扩展已有summary/metrics，不新增监控服务。assistant最终usage只计一次，reasoning属于output子项；压缩费用另行正确归因。时间优先用已有session写入时间/消息timestamp和检查回执，标明exact/estimated/unknown。活动检查、中断尾部和异常流不制造已完成耗时。

频繁board刷新只读当前状态和有限证据，不引入全量会话解析。精确日志hash留在明确验收路径。只有基线显示重复扫描显著时才增加可失效的增量游标/内存缓存；处理截断、替换、重启，不能用缓存绕过最终原证核验。磁盘扫描的重复与周期也先测量，不盲目提高刷新频率。

## C. 资源受控的多核执行

### 本机试验策略

已观测机器14核/36GiB；这些是本次实验参数，不写死到公共插件。CPU空闲不代表可以忽略内存，空闲内存字段也不等同于可分配上限。

初始并发为2个明确资源独立的check；重型浏览器/容器或资源未知的check默认独占。先实测1路与2路，正确且更快、内存压力正常时才试4路。不会以满核为指标：目标是等价结果的墙钟缩短、内存有余量和没有遗留进程。

本机后续合同可先为受控check子树设置8GiB的估算总预算、为系统/桌面/已有业务负载保留余量；这只是保守起点，不是可用内存测量或OS硬限制，须根据观测修订。Docker的guest内存上限和host RSS不可简单相加或重复计入；容器/虚拟机归属无法可靠测量时，其check独占。不要自动修改Docker分配或系统设置。

### 最小机制与边界

首先利用Pi原生codemode批处理；检查许可在现有check入口执行。只有合同明确声明可并行、资源独立和有限估算的检查能进入并发组；未声明保持串行。CPU估算包含子runner的线程/进程，避免外层×内层并发叠加。共享输出目录、数据库、端口、容器名或Git变更的检查互斥；最终候选验证期间不并行写源码/提交。

在同一worker内以一个小型check准入器限制active数量和已预留资源，不创建持久任务队列、DAG或第二份验收状态。等待不能持有board/SQLite锁；取消/异常必须释放许可。排队后、实际spawn前重新校验deadline、内存压力及候选条件，排队时间从同一预算扣除。内存高压停止新增并行，恢复后仍按原deadline判断；资源未知降低为单路而不是猜测充足。

此策略只控制插件check通道；bash手动启动的任意程序、已脱离进程组的程序、别的应用和其他插件实例不受它硬限制。文档必须说明软准入/采样限制，不能称为全机内存隔离。若多个插件实例并存导致可复现超额，再设计最小跨实例许可；本轮不预建全机调度服务。不自动杀无归属进程。

### 验证

用插件自有、各自临时目录和受控子进程的CPU、I/O、内存合成检查对照1/2/4路；每项读取与结果保持相同。测墙钟、峰值RSS/内存压力、有效并发、排队时间及残留进程。覆盖共享资源独占、未知资源、压力升高、排队耗尽预算、取消许可释放、嵌套codemode截止与失败不丢失。高并发更慢或有内存压力则保留更低值，不伪造加速阈值。

## D. 把计划与上下文优化放在同一执行闭环

廉价前提先核：在现有task-packet中明确本任务需要的准确基线、工具、目录/输入权限和真实检查命令。preconditions文本不冒充自动检查；用合成任务证明前提失败后依赖的昂贵子命令没有启动。无需消费项目业务规则或新preflight工具。

codemode批处理只合并独立读取/筛选，保留失败及原证引用；小输出直接调用，大输出本地筛选。用同一固定合成任务记录直接调用与批处理的实际往返/输出/用量，不能拿不同任务比较节省。

原生compaction属于受控验证，不阻塞A/C的主要提速。只在工具空闲和预算足够的安全边界调用，保留同session、原始会话、合同/候选/缺项、失败历史、store恢复和模型pins；计入压缩费用与缓存重建影响。先提供经过验证的显式方式或建议；没有可靠收益证据不默认自动压缩，不换session逃避上下文，不另建摘要库。

## 顺序、验收和交付

执行顺序：A实现→A自用终验→B插件基线/流式处理/指标→C有界并发实测→D计划与上下文闭环→精确组合候选最终验收。六项授权均有对应位置，但不同时堆进一个Pi任务。每段在原生Codex-Pi流程内派发、审查、整合；保持失败计数、原证和冻结helper，不将新增授权混入活动轮次。

开发用受影响定向测试；同一最终候选完整回归只跑必要次数。最终仍运行Python完整套件、真实Pi扩展/QuickJS、同task采用与真实worker交付、隐私扫描，并对照性能证据。性能记录写明基线/候选、环境、资源、实际工作量和测量方法；墙钟、RSS、token及必要检查数分别报告。没有等价对照就只报告事实和限制。

每段预算单独在真实合同中冻结；不以本路线默许延长现有四小时任务，不提高业务项目预算。公开文档只保留脱敏结论，原始样本/会话/主机指标存私有目录。完成标准是实际行为和可核证据，不是新增配置/文档、局部PASS或cpu占用率更高。
